## Scope

This regression checks that the published protocol, templates, and synthetic fixtures are mutually consistent. It does not claim to be a live two-agent concurrency execution.

## Checks

### Correct routing — PASS

Fixture A provides one explicit workspace/project mapping. `skill/SKILL.md` and the runtime templates prioritize explicit `project_id`, then exact workspace root/name, and require exactly one project by default.

### Wrong-workspace refusal — PASS

Fixture B requires refusal with no binding/runtime write. `skill/SKILL.md` explicitly requires stopping when a bootstrap names a different workspace than the one directly observed.

### Project isolation — PASS

The operating contract restricts reads/writes to the selected project plus minimum explicitly required shared references, and forbids importing state from similarly named projects or prior chats.

### Provenance separation — PASS

Fixture D requires directly verified evidence to remain separate from unverified/historical claims. The skill operating contract and PROJECT/SESSION templates preserve that distinction.

### Pre-write refresh — PASS

The session protocol and concurrency document both require re-reading the latest authoritative project state before a shared write.

### Stale SHA detection — PASS

Fixture C starts sessions A and B at `P0`. After A produces `P1`, B must detect `P1 != P0`; the published protocol explicitly classifies B as stale and forbids blind overwrite.

### Two-session reconciliation semantics — PASS (static)

The concurrency contract requires B to inspect intervening state, preserve A's compatible finding, merge B's compatible change, and produce a new state without a lost update. Semantic conflicts must remain explicit rather than being silently resolved.

### Session-log separation — PASS

Detailed work may be written to a session-specific path while only durable current-state changes are merged into `PROJECT.md`, reducing contention on the authoritative record.

## Pending live validation

A live synthetic concurrency test is still required to validate agent behavior rather than protocol text alone. The required scenario is defined in `tests/LIVE_CONCURRENCY_TEST.md`.

## Release verdict

`0.1.0` is internally consistent enough for controlled testing against schema 1. Do not treat the two-session concurrency behavior as live-validated until the live synthetic test has passed.
